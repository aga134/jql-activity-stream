Security Policy

JQL Activity Stream · Last updated 1 September 2026

Summary

The app runs entirely on Atlassian’s infrastructure, stores nothing, and sends nothing to any host outside Atlassian. Every request it makes to Jira is made as the person using it, so Jira’s own permissions decide what it can read. Most of what a security review usually has to assess — a server, a database, a transfer, a sub-processor — does not exist here.

Where the app runs

It is a Forge app. Its code executes on compute operated by Atlassian, inside the customer’s own cloud environment, and it is eligible for Runs on Atlassian, which requires that an app use only Atlassian-hosted compute and storage and that it not transmit end-user data externally.

  • No storage. The app writes no customer data anywhere, including Forge storage. There is nothing held at rest and therefore nothing to encrypt, retain, or delete on request.
  • No egress. The app makes no request to any host outside Atlassian. There are no analytics calls, no logging to a third party, no external model calls.
  • No sub-processors. We engage no third party to process customer data on our behalf.

Permissions

The app requests a single scope, read:jira-work, and it is read-only. No write scope is requested. No storage scope is requested, because the app persists nothing.

Every call is made with the acting user’s own authority, never with the app’s. The app cannot read a work item that the person using it could not open themselves, and a permission change in Jira takes effect for the app immediately, because Jira is the thing enforcing it.

How changes reach production

  • Source is held in version control with multi-factor authentication required on the account.
  • Changes are reviewed before deployment, and the automated test suite and forge lint must pass.
  • Dependencies are audited with npm audit before each release; advisories affecting production dependencies are treated as defects rather than noise.
  • There are no production credentials to rotate, because there is no external system to authenticate against.

Reporting a vulnerability

Email jqlactivitystream@proton.me. Please include what you did, what you saw, and which app and version. If it is easier, the public issue tracker at github.com/aga134/jql-activity-stream/issues also reaches us — but for anything that could expose data, prefer email.

What to expect:

  • Acknowledgement within 24 hours, even when the answer is only that we have received it and are looking.
  • An attempt to reproduce it, and a question back rather than a silent close if we cannot.
  • Notice when the fix ships, and credit if you would like it.

We will not pursue anyone who reports a genuine issue in good faith.

Fix timelines

Fix deadlines by severity are set by Atlassian’s Marketplace Bug Fix Policy, and that policy — not this page — is the commitment. It is read at the point of an incident rather than summarised here, because it changes.

If an incident happens

  • Atlassian is told through the Developer and Marketplace Support portal.
  • Affected customers are told if a vulnerability could have exposed their data, with what was affected, what to do, and when it was fixed.
  • A written response plan exists and is followed rather than improvised. Because the app holds no data and has no egress, the ceiling on any data-exposure defect is what the acting user could already see — but that is verified each time rather than assumed.

What we do not claim

This is a small independent operation, not a certified enterprise vendor. There is no SOC 2 or ISO 27001 certification, no external penetration test, and no 24/7 on-call rota. The security of this app rests on how little it is able to do: one read-only scope, no storage, no egress, and the platform enforcing permissions rather than the app.
